Abstract

Modern datacenter traffic increasingly crosses several contended links in series, yet deployable RDMA congestion control is evaluated almost exclusively on single-bottleneck benchmarks. We present an empirical study of multi-bottleneck fairness on lossless RDMA fabrics. On a parameterized parking-lot benchmark with a fluid max-min oracle, every deployable scheme we test is unfair to the multi-bottleneck flow — DCQCN 1.7–2.3×, TIMELY 1.8–2.0×, DCTCP 1.6–1.8×, HPCC 1.9–2.0× — growing with bottleneck count and robust to start-time jitter. For HPCC we localize the mechanism: a near-winner-take-all equilibrium in which the multi-bottleneck flow collapses to ~0.4 Gbps. Six sender-only corrections fail — including a sender-side mirror of RCP driven by the same INT signals: private, independently maintained copies of an explicit-rate recursion preserve arrival-history asymmetry indefinitely, while one shared per-link register erases it. Per-flow fair queueing equalizes only what the endpoint offers — 1.97× windowed, equal-but-idle (13× oracle FCT) windowless. Placing the register at the switch — RDMA-RCP, an RCP service mode carried in one 64-bit INT field with three words of mutable state per port — restores the max-min allocation (penalty ≈1.005×; flows within 5–13% of oracle FCT in the heterogeneous matrix, a uniform 21–39% under three-factor compound stress) with zero PFC in every fairness experiment, rate-only or with a canonical cwnd = R·RTT window, and cuts a ring-collective coflow's completion time by 18–23% at every seed tested (18% with the INT header padded to stock size); on a saturating k=6 fabric, makespan improves 14%. We equally measure where the mode does not belong: it cannot share an unsliced link with stock HPCC, and at fan-in past ~64 it sustains only 25–50% utilization (a standing limitation; the adopted-rate floor bounds feasible fan-in at C/Rfloor). We also measure the deployment boundary: RCP-mode and HPCC traffic do not coexist fairly on a shared link — even under a weighted-DRR reservation, because the classes' control signals remain port-global — so per-class deployment needs sliced telemetry or a separate fabric. Stock HPCC remains byte-for-byte unchanged alongside.

Baseline reproduction (this artifact)

The simulator is the original HPCC code base upgraded to ns-3.45 (interface-level changes only). Before extending it we verified the upgrade still reproduces the original SIGCOMM '19 results — all five congestion-control schemes × two workloads (WebSearch, FB_Hadoop) × three loads, on the full 376-node fat-tree. Build & reproduce

The repository is the original HPCC simulator, modernized: the code base is upgraded to a tagged ns-3.45 release with interface-level changes only, with every module re-tested so the whole tree compiles and runs on modern ns-3. The full tree is therefore required to build and run (it is not a drop-in patch on the upstream repo). Quick start:

# build the optimized binary
bash examples/hpcc/algorithm-validation/run.sh --optimized --build-only

# generate a parking-lot config, run HPCC-FS (cc_mode 11), and check fairness
python examples/hpcc/hpcc-fs/gen_parking_lot.py --n 4 --cc-mode 11
# expect: UNFAIRNESS ... = 1.005x,  PFC = 0

Full instructions, the claims→experiments map, and the engine-change table are in the repository README.
